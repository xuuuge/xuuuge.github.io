In my first GPU Mode competition, I finished 22nd out of 107 participants after spending almost $200 on Modal and OpenAI combined. I made the baseline roughly 4× faster, yet the winning solution was still almost 2.7× faster than mine. This post shares what I learned and what the experience made me think about programming and multi-agent orchestration.

What is GPU Mode?

GPU Mode is a community that runs public competitions to optimize GPU operations used in large language models.

These are not merely isolated benchmark exercises: they target the same operations and inference paths used in real LLM systems. For example, in March 2026, AMD launched a GPU MODE virtual hackathon focused on LLM inference on AMD GPUs [1]. Solutions from the competition were later used in AMD’s vLLM stack [2].

The problem: Cholesky decomposition

Cholesky is simple. Given a symmetric, positive-definite matrix A, find a lower-triangular matrix L that satisfies:

A = L × Lᵀ

It is like finding the square root of a matrix.

A = 422 253 236 = 200 120 112 × 211 021 002

The middle matrix is L; the right matrix is LT.

Input shape

Each input has shape (batch, n, n): batch is the number of matrices that arrive together, and every matrix is n × n. For example, 4096 × 32 means 4,096 independent 32 × 32 matrices. The leaderboard measures latency for each shape separately: one call must finish before the next begins.

Multiple input shapes make the problem much more interesting: every shape has different bottlenecks and requires specialized kernels for full optimization. The table below shows the theoretical bounds and parallelization style for each shape. These bounds do not account for Cholesky’s stage dependencies. Naive algorithm

Naive Cholesky builds L one column at a time.

  1. Find the diagonal value with a square root.
  2. Use it to derive every value below it in the same column.
  3. Remove that column’s contribution from the remaining matrix.
  4. Repeat.

If you are familiar with GPU work, your radar is probably already alarming: this problem has stage dependencies, so the GPU spends a lot of time idle and waiting. The column-by-column calculation also has low arithmetic intensity [4], meaning the diagonal stage severely underutilizes the GPU.

These bottlenecks are what the shape-specific optimizations in the next section try to address.

My solutions

My solution extends the naive approach with shape-specific optimizations tailored to the B200 hardware and each shape’s constraints. Here are the optimizations:

37 frontier milestones are shown, plus the invalid reset incident, which I will talk about later. I used a 0.2% total-score cutoff for the retained frontier.

The optimizations fell into six broad categories:

  • Lower precision: using TF32 updates, FP16 inputs with FP32 accumulation, FP16 panel storage, and mixed-precision SYRK.
  • Approximate, then verify: using Newton–Schulz, triangular Newton updates, fast reciprocal square root, and inverse-based TRSM, with validation and exact repair for difficult cases.
  • More parallelism: using warp-level kernels, multiple matrices per CTA, multi-CTA updates, TMEM clusters, overlapping execution lanes, PDL, and CLC lookahead.
  • Lower launch overhead: using CUDA Graphs, direct kernel launches, fused operations, persistent preparation, and fixed cuBLASLt plans.
  • Less memory movement: computing only the lower triangle, removing upper-zero and seed-copy work, fusing triangular copies, and reusing materialized panels.
  • Better decomposition and specialization: moving between right-looking and left-looking formulations, splitting diagonal and panel work, co-designing block sizes, and choosing routes for each matrix and batch size.
The 526.6 µs loophole: how I was rank 1 for two days

During the competition, the agent found a loophole by merging the inputs together and producing their outputs at the same time. That essentially made the different shapes meaningless. As a result, I was rank 1 for two days. 😄 Even though I directly confronted the agent about the issue, it said that, after reading the rules, this seemed borderline fine. A week later, the organizer fixed the loophole. This corroborates the anecdotes we hear online about agents exploiting benchmarks for a better score. Nonetheless, it was very cool to see it happen with my own eyes. 👀

Agentic flow

I mainly use Sol5.6 with varying effort levels for different workflows.

  • I asked the agent to aggressively consider lower-precision calculations.
  • I asked it to try Newton–Schulz to approximate the matrix inverse in the panel stage.
  • When progress stalled at around 650 µs, I asked it to change the architecture dramatically and keep optimizing the new design even when its first version was slower. The model was a bit stubborn at first, prematurely deciding that the new architecture was too slow. After I consistently prompted it to try for 10+ rounds, the architecture finally caught up.

Reference: MLSys 2026 FlashInfer AI Kernel Generation Contest [5], where I drew inspiration for the agentic workflow.

Rank 1 solution analysis

Remember how dependent stages are bad for GPUs, and how working column by column makes the arithmetic intensity especially poor? Rank 1 found ways around that loop by relaxing two constraints:

  • The factor does not need to be bit-for-bit exact, only accurate enough to pass the checker.
  • The benchmark inputs come from a predictable distribution.

The winning solution combines several ideas.

1. Jacobi

Jacobi does not produce L in one pass. Instead, it starts from a rough guess and updates the whole lower triangle in a small number of waves. Each wave measures the residual A − LLT from the same previous snapshot, then dampens that residual into the next guess. Think of it like gradient descent toward the real L: many tiles can move together instead of waiting for the previous column to finish.

The update rule
Lii0 = Aii Lij0 = Aij Ajj (i > j) R(t) = A− L(t) (L(t)) T Lij(t+1) = Lij(t) + αt Rij(t) Ljj(t) (i > j) Lii(t+1) = (Lii(t)) 2 + βt Rii(t)

αt and βt control the damping. This is the core correction in the winning Jacobi kernels; some routes also add momentum and lower-precision storage.

2. Polynomial

Polynomial approximation is used to estimate L−1. How many powers we keep depends on the acceptable error and the input distribution. The Rank 1 solution uses cutoffs of 6 for 512 × 512, 4 for 1024 × 1024, and 2 for 2048 × 2048. For the 2048 case, this approximation is quite extreme: it keeps only two terms. It relies heavily on the input matrices being very close to I; this approximation would not work for arbitrary matrices. Here is the formula:

F−1 = (I+T) −1 = I−T+ T2− T3+⋯.

Runtime analysis

Ours/classical: Θ(Bn3), few FLOPs, serial frontiers Global Jacobi: Θ(Bkn3), many FLOPs, highly parallel Block polynomial: Θ(Bn3+B(p+q)nb2), near-classical work, fewer serial scalar operations

B = batch · n = matrix size · b = block size · p = factor-refinement steps · q = inverse-polynomial degree

Although their theoretical runtimes can be higher, these approaches are often faster in practice because they expose more parallelism, increase arithmetic intensity, and reduce dependency stalls.

Reflection on Rank 1 solution

You might be thinking: isn’t this cheating by exploiting how the benchmark data is generated? What if the secret dataset follows a different distribution? My view is that this actually makes the problem more similar to real LLM and kernel optimization. Efficient implementations rarely optimize for every mathematically possible input. Instead, they exploit the structure and distributions that occur in real workloads.

Quantization is one example: FP16-to-INT8 error depends strongly on the activation distribution. SmoothQuant [6] uses that distribution to rescale channels, reducing the effect of outliers before rounding to INT8.

Muon [7] is another example. Rather than perform an expensive exact orthogonalization, it uses a few fixed Newton–Schulz iterations, a polynomial approximation that works well for the momentum matrices encountered during training.

In both cases, the optimization works not by handling every possible input equally well, but by taking advantage of the structure found in the workload that actually matters. When inputs are not well behaved, normalization or rescaling can often bring them into a regime where these approximations remain reliable.

Other solutions

To my surprise, ranks 2, 8, and 9 did not really use the strategies from the Rank 1 solution. They were mostly extensions of the naive algorithm. Rank 2 made more than 9,000 submissions, while Rank 1 made only 28. That tells part of the story: insight can get you to a strong solution quickly, while brute-force iteration can reach similar performance if you keep going long enough. As an aside, it would be interesting to plot performance against token cost and see this tradeoff directly.

Postmortem reflections

After studying the other solutions alongside my own, here are my reflections and what I would do differently next time.

  1. Start with a hierarchy of languages: use Triton to identify promising directions, then move to lower-level languages only when needed (Tri Dao has a good interview about onboarding PhD students to these languages [3]). This substantially reduces trial cost. In addition, Sol5.6 [8] is specifically trained for Gluon and Triton.
  2. The code became too messy. I did not steer the agents strongly enough toward composable code.
  3. Spending a few hours upfront to define the harness, such as the submission and logging workflows, is important. Iteration was slow because the submission instructions were unclear: there were conflicting rules about when to submit to the leaderboard versus when to use Modal for logging.
  4. My central-agent design created context pollution. Many success stories use separate agents for separate workstreams instead.
  5. I expected most of the gains to come from B200-specific paradigms. In practice, exploiting the numerical-precision boundary and inferred input-generation method mattered more.
  6. I started with Claude and later switched to OpenAI to reduce costs. That transition left behind duplicate README and agent files.

Agent failure patterns I found

  1. The agents often gave up too early and settled into local minima. In the postmortem, I learned that we had considered Jacobi, but discarded it because it was slower than the current solution. A cleaner context agent, or a fleet of independent agents, could make it easier to revisit such paths.
  2. Tenacity could also hurt: an agent might spend too long trying to fix its low-level-language implementation instead of reconsidering its workflow. It still needed external steering for that kind of meta-learning.
  3. Centralized control caused major context growth and pollution. At times, Sol5.6 would do work itself instead of spawning a requested subagent. This connects with Alex Zhang’s discussion of harnesses and compositional generalization [9].

Closing thoughts

I learned a great deal from this competition. Six months ago, we were still struggling to get a single agent to write a helper function; now the challenge is managing a fleet of agents. The problem space and the skills it demands has changed quickly.

Many of these lessons only become clear through doing the work, which is one thing humans are better at: high-level intuition and meta-learning.

This article will be useful for myself to look back on some of the metapoints, I hope it’s useful for you too!
